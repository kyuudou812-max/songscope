# 自己成長アプリ 設計方針書

対象ユーザー：本人（減量／TOEIC 230→600）専用アプリ。
入力資料：`自己成長アプリ設計用_ユーザー行動特性・リスクプロファイル`（58項目）。

このドキュメントは、あの58項目を機能一覧に直訳する前に、
**「何を代行し、何を補助し、何を本人にやらせるか」** という設計の土台を先に固定するためのものです。
機能を思いついた時点で毎回この文書に立ち返り、矛盾していないかを確認してください。

---

## 0. 起点の問い（資料58番）への回答

> このユーザーがこのアプリを6か月使用した結果、
> 体重管理／TOEIC学習／優先順位決定／着手／中断からの復帰／プロジェクト数の制御 について、
> 本人自身の能力が上がっているためには、アプリは何を代行し、何を補助し、何を本人にやらせるべきか？

| 領域 | 代行（アプリがやる） | 補助（アプリが支援する） | 本人がやる（伸ばす対象） |
|---|---|---|---|
| 体重管理 | 体重・行動ログの保存、トレンド計算、短期変動のノイズ除去 | 「今日の1行動」の提示、停滞時の仮説提示 | 食事・運動の実行、体感の解釈 |
| TOEIC学習 | 進捗の記録、ボトルネック領域の可視化（文法/語彙/L/R） | 次にやる1問／1教材の提示、模試結果からの弱点抽出 | 実際に解く、教材選定の最終判断（Stage 3以降） |
| 優先順位決定 | 選択肢を2〜3個に絞り込む | Stage別に「決定→2択→本人選択→本人選択+レビュー」と支援を逓減 | 最終判断そのもの（早期にAI依存させない） |
| 着手（0→1） | 開始動作を1タスク・1クリックまで極小化 | 「今これだけ」の1行表示 | 着手する行為自体 |
| 中断からの復帰 | 停止日数の検知、Recovery Modeへの自動切替 | 通常計画を隠し、5分版タスクだけ提示 | 実際に再開する判断と行動 |
| プロジェクト数制御 | Active上限（Main2本／Growth1本）のハード制約、超過時のブロック | 新規追加時に「何をやめるか」を問う | 何を止めるかの意思決定 |

**設計原則として確定させること：**
「本人が習得すべき能力（優先順位決定・着手・復帰・取捨選択）」を自動化してはいけない。
自動化していいのは「データの保存・集計・提示の整形」だけ。
この境界線（資料24番のA/B分類）を、新機能を追加するたび最初に判定する。

## 1. アプリの性質定義

- これは **Motivation App ではない**（資料49番）。褒める・盛り上げる・streakで釣る設計を採らない。
- これは **Executive System**：「何をするか→いつするか→今何をするか→やったか→何が起きたか→次をどう変えるか」を回す装置。
- 成功指標はアプリ内指標ではなく、**現実世界の結果**：
  - 実際に英語をした日数・内容
  - 実際に食事・運動行動が変わったか
  - TOEIC本番のスコア
  - 体重の長期トレンド
- **アプリ開発自体の完成度は評価指標にしない**（資料3番）。新機能は「Main Goalの現実行動が増えるか」で採否を決める（資料41番・52番のチェックリスト）。

---

## 2. 領域構造（Main / Growth / Playground）

```
Main Goal（固定2本、変更不可・追加不可）
 ├─ BODY   健康体重までの減量
 └─ ENGLISH TOEIC 230→600

Growth（Active上限1本）
 ├─ 資格・ITスキル・成果物など「将来価値を上げる活動」
 └─ Idea Inbox（Capture自由・Start制限）

Playground（別枠・監視対象）
 └─ 面白そうだから作るもの。Main Goalを侵食していないかだけ定期チェック。
```

- Main Goalは常に2本固定。増減はアプリ側で提案しない（資料16番）。
- Growth領域で新規Activeにする際は、既存Activeを1つ選んで停止/完了させない限り追加できない（資料33・34番、ハード制約として実装）。
- Idea Inboxへの追加は10秒以内・1タップ（資料14・15番）。カテゴリ・優先度は後でAIが1問ずつ質問する（資料39番）。

## 3. ホーム画面（情報設計）

資料21・22番に従い、ホームは「見る」より「次に何をするか」を先に出す。グラフはホームに置かない。

```
NEXT ACTION
▶ 今これをやる（1件、多くて2〜3候補）

TODAY
BODY     ○ 今日の行動（1行）
ENGLISH  ○ 今日の行動（1行）
GROWTH   ○ 現在の1プロジェクトの次の一歩
```

- 詳細分析・グラフ・履歴はすべて別画面に隔離してよい（そこは複雑でも構わない）。
- ホームで見せる「行動」は常に開始動作レベルまで分解済みのもの（例：「テキストを開く」）であり、「30分勉強する」のような時間ノルマ表現にしない（資料4番）。

## 4. AI Coachの振る舞い規約

1. **事実と推測を必ず分離する**（資料18番）。
   - 事実：「過去7日間の英語実施日は1日」
   - 推測：「学習開始の摩擦が増えている可能性があります」
   - UI上もラベルを分けて表示する（例：`観測`/`推測`のタグ）。
2. **過度に褒めない・過度に詰めない**（資料19・20番）。分析者＋コーチのトーン。評価対象は結果だけでなく「復帰・着手・実験・行動修正」も含める。
3. **質問は一度に1つ**（資料39番）。フォーム化しない。
4. **白紙で聞かない**（資料40番）。「今後どうしたい？」ではなく「AとBどちらを優先する？」の形にする。ただし段階的に白紙質問の比率を上げてよい（Stage設計と連動）。
5. **通常時は質問しない**（資料38番）。異常検知時のみ介入：
   - 3日未実施 → 原因を1つ選択させる（選択式、自由記述強制なし）
   - 7日未実施 → Recovery Modeへ自動遷移
6. **健康領域で断定しない**（資料48番）。「これなら必ず痩せる」等は禁止。記録・行動支援・傾向分析に役割を限定する。

## 5. 支援逓減（Scaffolding Decay）— 優先順位決定の段階設計

資料23・50・51番。永久にAIが決めない。段階を明示的にDBへ持たせ、本人ごと・領域ごとに進捗を記録する。

| Stage | AIの振る舞い | 進級条件（例） |
|---|---|---|
| 1 | AIが次の行動を決定して提示 | 初期状態 |
| 2 | AIが2択を提示、本人が選ぶ | Stage1を一定期間安定運用 |
| 3 | 本人が選択、AIは提示なし | 本人選択の実行率が閾値を超える |
| 4 | 本人が選択・実行し、AIは事後レビューのみ | 継続 |

- 降格もあり得る（7日以上の停止でStageを一段階戻す、など）。これも「失敗扱い」ではなく通常運転として設計する。
- 「以前：AIが決定 → 現在：本人が選択」のような**遷移自体を成長ログとして記録**する（資料51番）。これはStreakより価値のある成長指標。

## 6. Recovery Mode（復帰設計）

資料10・11番：連続記録（Streak）を中心指標にしない。**復帰速度**を成長指標にする。

- 主要指標：「止まってから何日で戻れたか」（Streak日数ではない）。
- トリガー例（ENGLISH）：
  1. 7日間ENGLISH行動ゼロを検知
  2. 通常学習計画を非表示にする
  3. 「今日は5分だけ前回教材を開く」など最小行動のみ提示
  4. 実行が1回確認されたら通常計画へ復帰
- Recovery Modeへの遷移は「失敗の記録」ではなく状態遷移として扱い、ネガティブなラベル（赤色警告など）を避ける。
- 新方式・新教材への切り替えは、まず「既存方式を最小単位で再実行」を1回試すステップを必ず挟む（資料7番）。これによって「本当に方式が悪いのか、単に数日空いただけか」を切り分ける。

## 7. データモデル原則

### 7.1 記録するデータの条件（資料43番）
以下のどちらかを満たす項目だけを記録する。「いつか分析できるかもしれない」は理由にならない。
1. 現在の判断（NEXT ACTIONの決定、Recovery判定など）に使う。
2. 明確な将来仮説（Experiment）の検証に使う。

### 7.2 入力負荷（資料13・14番）
- 手入力は原則10秒以内。
- 「大量に保存するが、本人にはほとんど入力させない」を徹底：自動取得・デフォルト値・選択肢・後追い入力を優先。
- 例：資格候補を思いついたら名前だけ保存 → カテゴリ・優先度はAIが後で1問ずつ質問。

### 7.3 指標の階層分離（資料17番）
「やった量」だけを評価しない。Input／Process／Output／Outcomeを分離して保持する。

```
ENGLISH の例
Input   : 学習時間
Process : 解いた問題数
Output  : 模試結果
Outcome : TOEIC本番点
```

ホームやコーチの発言は基本的にOutcome/Outputに重心を置き、Inputだけの最適化（勉強時間だけが伸びる状態）を強化しない。

### 7.4 信頼性（資料42番、ただし過剰設計注意）
- stable ID、履歴の追記のみ（上書きしない）、原データ保持、schema version、backup/restoreは必須要件。
- ただしMVPでは「壊れない」ことを優先し、migration機構などは実際に2回目のschema変更が必要になった時点で導入する（先回りして複雑化しない）。

## 8. Experiment機能（資料30・31・32番）

行動変更は「なんとなく変える」のではなく実験として扱う。

- 1件のExperimentは以下を持つ：仮説／変更内容／期間（例：14日）／評価指標／結果／採用or棄却。
- **一度に変更する主要因は1つ**（複数同時変更を禁止、UIレベルでブロックする）。
- 採用・棄却された変更は「設計変更履歴」として時系列に残す（例：「9/10 英語開始時間を22:00→19:30、理由：夜は未実施率が高い、結果：14日後に判定」）。
- 資料56番の未検証事項（朝型/夜型、学習単位の長さ、通知の効果、Gamification/競争/金銭ペナルティの効果、最適な減量ペース等）は、**設計者が決め打ちせず、すべてExperimentとして検証対象にする**。

## 9. 目標追加時のコスト提示（資料33・34番）

新しいGrowth Projectや資格をActive化しようとした時、単純な追加ボタンを置かない。

```
新しい資格をActiveにしますか？

現在のActive:
 Main:   TOEIC / 減量
 Growth: 基本情報技術者

この資格を開始すると Growth Active が2件になります。
何を停止しますか？
[ 基本情報技術者を Pause する ]
[ 今回は Idea Inbox に留める ]
```

- Pause / Drop / Finish を明確に区別し、Dropを失敗として扱わない（資料35番）。意図的な中止も正しい意思決定として記録する。
- 状態は Active / Waiting / Scheduled / Idea / Done / Dropped の6値で管理する（資料36番）。

## 10. 新機能追加チェックリスト（資料52・53番）

新機能を実装する前に、この5問に**すべて**答える。1つでも答えられなければ実装しない。

1. この機能はどの現実行動（実際の減量行動／英語学習行動）を変えるのか？
2. 既存機能で代替できないか？
3. 入力負荷はいくら増えるか？
4. 本人の「仕組み作りへの逃避」を助長しないか？
5. Main Goal（減量・TOEIC）にどう寄与するか？

**恒久的に禁止する実装パターン**（資料53番）：
- 最初から巨大なアプリを設計する
- 何でもダッシュボード化する
- Gamificationの大量投入
- 目的のないAI機能追加
- 毎日大量の通知
- Streakを中心指標にする
- 全自動化（本人の判断力を伸ばす領域まで代行する）
- 新しい目標を簡単にActive化できるようにする
- 詳細な感情日記の必須化
- 完璧な人生管理システムを最初から作ろうとする

## 11. MVP スコープ（資料54番）

**MVPで証明すべきことは1つだけ**：このアプリを使うことで減量行動と英語学習行動が実際に増えるか。

含める：
- BODY（体重・行動ログの最小記録、トレンド表示は詳細画面に分離）
- ENGLISH（今日の1行動提示、Input/Process/Output/Outcomeの最小記録）
- NEXT ACTION（ホーム最上部、1件〜多くて3件）
- 簡易記録（10秒以内の入力）
- Recovery Mode（7日未実施での自動切替）

含めない（後回し）：
- 資格管理、GitHub連携、Playground管理
- 詳細分析ダッシュボード
- Scaffolding Decayの4段階すべて（MVPはStage 1のみで開始してよい）
- Experiment機能のUI化（最初は設計変更履歴を手動メモでも可）

**運用ルール（資料8番）**：v1を最低14日間実運用するまで機能追加を禁止する。改善したくなった項目はIdea Inboxに退避し、14日経過後にまとめて評価する。

## 12. 実装上の補足（このリポジトリについて）

現在のリポジトリ `songscope` は本設計と無関係な既存プロダクト（カラオケ録音・採点PWA）です。本設計に基づくアプリは、既存コードと衝突しないよう `self-growth-app/` 配下で独立に構築することを想定しています（本ドキュメントもその配下に設置）。

次のステップとして想定されるもの（着手前に本人へ確認が必要な事項）：
- 技術スタック（既存songscopeと同様のVanilla JS PWA構成にするか、別スタックにするか）
- 単一デバイス運用か、複数デバイス同期が必要か（バックエンド有無に直結する）
- 既存songscopeと同一リポジトリ内で運用し続けるか、別リポジトリへ分離するか

これらが決まり次第、本ドキュメントのMVPスコープ（第11章）をそのまま実装タスクへ分解できる状態にしてあります。
